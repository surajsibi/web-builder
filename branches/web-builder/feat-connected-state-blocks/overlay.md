# Repository overlay — web-builder / feat/connected-state-blocks

## Verified repository differences

- `ComponentTemplate` and `ResolvedComponentTemplate` expose optional private `key`, trimmed `nameHint`, `nodeReferences`, and template `stateBinding` metadata. Resolution preserves authored metadata in isolated resolved templates for later compiler phases while leaving legacy resolved nodes free of those fields.
- Template validation enforces `^[a-z][a-z0-9-]{0,63}$` without normalization for declarations and referenced keys, rejects duplicate declarations through one template-wide `Map`, validates the authored relationship shapes, and enforces a trimmed 1-80 character `nameHint` bound before ordinary component resolution.
- `BlockDefinition.library` is the validated authority for label, category, family, icon, and optional search terms. Every existing block declares an explicit `navbar`, `buttons`, or `inputs` family, and Component Library consumers no longer infer a family from category display text.
- Existing block roots, absence of optional metadata on legacy templates, Component Library behavior, Editor Shell labels, and the public `block.insert` result remain compatible in the focused regression evidence.
- Template resolution collects the complete key-to-path-and-type declaration index before relationship checks, so valid forward and sibling references resolve without traversal-order dependence. It uses component-registry reference metadata as the only authority for declared node-reference paths and target component types.
- Symbolic validation rejects dangling prop and state-binding keys, undeclared or duplicate reference paths, wrong prop-reference and state-binding target types, non-empty raw node references, any visibility binding owned by a Boolean State, and a Boolean State root on a registered block. Final component strict-props validation runs only after these relationship checks.
- Valid symbolic references remain private resolved-template metadata until `block.insert`; their raw component props remain empty during resolution, and the resolver itself neither allocates IDs nor mutates documents.
- In apply mode, `block.insert` flattens the validated resolved tree in preorder, reserves every project-wide unique real ID before node construction, and builds both template-object-to-ID and private local-key-to-ID maps. Reference props and visibility bindings receive only those real IDs.
- Every materialized component prop object and state binding passes its current strict schema before the source document is cloned. All nodes are built in isolated memory, then the candidate receives the complete subtree through the existing one-root insertion path; an allocation or materialization rejection leaves the source document unchanged.
- A trimmed `nameHint` becomes the node's readable base name. Existing page names and names claimed by earlier nodes in the same insertion are reserved in preorder; collisions receive deterministic suffixes beginning at `2`. Templates without hints retain the existing type-derived naming behavior.
- Dry-run executes all materialization-independent validation without consuming generated IDs. Apply-only generated-ID exhaustion or collision is rejected before candidate construction. The command still returns only `blockType`, `rootNodeId`, ordered `nodeIds`, and `destination`; no alias, hint, symbolic relationship, placeholder, or `keyedNodeIds` field persists or escapes.
- CSB-04 and CSB-05 share one test-only connected template fixture; it remains outside the production registry and adds neither an Interactive library entry nor Disclosure accessibility semantics.
- Two independently inserted fixture instances have disjoint real node and Boolean State IDs, with each trigger and panel targeting only its own state. Each insertion remains one store commit and one history entry.
- Whole-root duplication follows the existing generic remap-if-target-cloned rule: the copied Button reference and copied panel visibility binding target the copied nested Boolean State, while the captured source document remains unchanged.
- Trigger-only and panel-only duplication preserve their existing external Boolean State target. Deleting the complete inserted root removes every nested node, including its state. Undo removes one inserted connected subtree and Redo restores the exact same ordinary nodes and relationships.
- CSB-05 required no production command, store, registry, schema, or runtime change. Button Disclosure configuration and effective accessibility semantics remain owned by CSB-06, and the production adopter remains owned by CSB-07.
- Button component version 6 persists `stateAccessibility: "none" | "disclosure"` and `disclosureContentNodeId`; version 5 migrates deterministically to disabled Disclosure configuration, versions 1 through 5 traverse the complete component migration chain, and project schema remains 3.
- Button registry metadata declares both `targetStateNodeId` to `boolean-state` and `disclosureContentNodeId` to `container` as page-scoped, `remap-if-target-cloned` references. Existing whole-page and whole-subtree duplication remaps both cloned targets without a special duplicate command.
- `node.updateProps` reconciles only direct Button edits. An incompatible direct edit clears Disclosure configuration in the same candidate and history entry; link or submit edits also clear incompatible state action data required by the existing Button schema. Unrelated edits preserve recoverable dangling configuration created by panel or tree changes.
- `evaluateDisclosureSemantics` is the single read-only authority for effective Button configuration, state target, controlled Container target, exact visibility binding, shared-parent structure, responsive presentation, ancestor visibility, and live runtime agreement. It returns derived status only and never dispatches, repairs, normalizes, or mutates the page.
- `NodeRenderingController` emits `aria-expanded` only for a valid effective result. Preview emits `false` or `true` with the live content state; Editor omits the collapsed attribute while its inactive authoring treatment intentionally keeps content visible, and emits `true` after the content becomes live.
- The State Inspector reports persisted Disclosure configuration separately from effective readiness. Ancestor state bindings without live runtime produce an informational runtime-dependence diagnostic instead of a false “Ready” result. Panel reconnection, shared-parent restoration, viewport reveal, and configuration clearing remain explicit; responsive reveal writes an active-layer visible override, and shared-parent restoration dry-runs every move against the original snapshot before mutation.
- Component definitions may provide an optional template-props validator that receives the set of symbolic registry-reference paths. Button uses it to accept only the unresolved state/content references required by its authored template configuration; it creates no placeholder, allocates no ID, and leaves final materialized props subject to the existing strict persisted schema.
- The production `disclosure` block is the only `interactive` adopter. Its visual Container root owns a native Button, a controlled Container with ordinary Text, and a nested Boolean State whose authored default is Off. The Button declares symbolic references to local keys `open` and `content`, and the controlled Container declares exactly On-to-Show / Off-to-Hide against `open`.
- `block.insert` materializes the Disclosure as five ordinary nodes with readable names: `Disclosure`, `Show details`, `Disclosure content`, `Disclosure details`, and `Disclosure open`. Both Button references and the visibility binding receive the instance's fresh real IDs; the root remains selected and the public result remains limited to `blockType`, `rootNodeId`, `nodeIds`, and `destination`.
- Component Library exposes a non-empty Interactive family and discovers Disclosure in All, Blocks, Interactive, favorites, and registry-owned search terms. Its representative preview renders the panel open using noninteractive spans and omits the nested Boolean State entirely.
- Production tests prove click insertion and drag translation share `block.insert`, Editor Layers expose the readable node names, Preview starts collapsed and preserves pointer/Enter/Space behavior with truthful `aria-expanded`, two insertions are disjoint, whole-root duplication remaps both Button references plus the panel binding, and explicit State Inspector reconnection restores a deliberately inverted production relationship.
- The command benchmark uses one committed revision-independent harness, a fixed 1,000-node fixture, 10 warm-ups, and 50 measured insertions for the 70-node Commerce Navbar and 5-node Disclosure. The reporter writes repository-relative JSON with every raw sample and UTF-8/LF logs; metadata binds exact source, harness, reporter, config, lockfile, and artifact identities.
- Same-machine Node 24.19.0 evidence against baseline `c032701` and committed candidate `40de821` records Commerce Navbar regressions of +3.25% median and -4.95% nearest-rank p95, both below Suraj's accepted 10% ceiling. Candidate Disclosure measures 38.4245 ms median and 51.1941 ms p95.
- Post-merge automated evidence under Node 24.19.0 passes typecheck and full ESLint. The serialized rerun passes 669 of 669 tests across 48 files in 285.05 seconds. The Next.js 16.3.0 optimized production build passes in 24.07 seconds, reports ready in 217 ms, and serves the dashboard `/` route with HTTP 200 and a 6,967-byte response. One non-blocking warning reports an ignored lockfile outside the repository. Together with the retained Chrome verification and fresh Firefox smoke, the sole remaining documented exception is NVDA/Firefox accessibility testing.
- At browser widths up to 48rem, the Editor replaces its three-column minimum-width workspace with one vertically scrollable column. The Component Library, Canvas, and Inspector remain full-width and preserve their expanded/collapsed controls; at up to 32rem, toolbar controls use a compact one-column arrangement. The desktop grid remains unchanged above the breakpoint.
- The root `<body>` uses React's scoped `suppressHydrationWarning` escape hatch for unavoidable attributes injected by installed browser extensions before hydration. In Chrome 151.0.7922.138, `cz-shortcut-listen="true"` remains present while Editor and Preview console checks stay clean; application-owned descendant mismatches are not suppressed by this body-level attribute.
- A fresh Playwright 1.62.1 headless Firefox 153.0 production smoke at 1440 x 900 passes dashboard HTTP 200, new-project Editor loading, Disclosure insertion, pointer expansion/collapse, Preview `aria-expanded` `false → true → false`, zero console/page errors, zero horizontal overflow, valid visible geometry, and visual inspection without an obvious regression.
